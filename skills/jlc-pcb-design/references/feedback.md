# 可选反馈与 Issue 归档

下单完成、收到制造审核结果或实板装配/debug阶段收尾时使用。不要求每次工具操作后反馈，不建立定时催问或自动创建 issue 的机制。

## 收集与选择归档

1. 邀请当前协作者提供简短反馈，可跳过或稍后补充；不影响已授权工作继续完成。下单侧关注审单、拼板、工艺、费用及交付，实板侧关注预期/实际、复现条件、测量与修复；只询问相关内容，不强制填写完整表单。
2. 收到有效反馈后，提炼用途：**改进 skill 的流程/方法、保留踩坑反面教材、提供新信息**。即使结论未知，也可以保存有证据的现象。
3. 准备具体标题、要点和拟归档仓库；能够只读查重时先查相关 issue，再询问协作者是否需要创建 issue。目标仓库不明确时一并确认，不默认把项目私有资料发送到 skill 仓库或公共仓库。
4. **协作者确认后才创建**，返回链接并在项目资料关联。已有同类 issue 时可建议关联或追加，仅在明确授权范围内更新。未答复、跳过或拒绝均不创建，不重复催问同一反馈。

## Issue 的最小内容

- 用途及涉及的项目/板版本/发布标签；不适用的字段可省略。
- 实际现象、预期、来源与证据；保留原始单位、日期及适用工艺/环境。
- 已知影响、临时处理和仍未知的部分；区分协作者反馈、代理推断与已验证原因。
- 拟改进的方法或需要补充的信息；原因未明可先保留观察，不强行总结通用结论。

只提交与问题有关的资料，发布前核对目标仓库可见性及内容范围。没有反馈不创建占位 issue；创建 issue 不等于已经修复问题或批准修改电路。

## 回到方法改进

反馈先保存为可追溯证据，排查验证后再决定是否修改项目文档或 skill。项目参数留在项目，版本故障留工具记录；通用改进抽象为步骤、验证或 reference，不把每个新案例加入主 context。
